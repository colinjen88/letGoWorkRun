# WANG 作品集網站升級改版計劃書

版本：研究提案 v1.0  
研究日期：2026-09-05  
網站：<https://let.gowork.run/>  
目標：提高來自 104 與主動投遞的合適面試機會，建立可核實的前端、網頁設計與 UI/UX 能力證據。  
本次交付：現況分析、外部研究、定位、資訊架構、視覺與互動方向、技術選型、內容規格、執行順序、驗收與成效追蹤。尚未實作或部署新版。

## 1. 核心判斷與建議

值得大幅改版，但主要投資應放在「職務定位、案例證據、設計品質與工程可信度」，再以合適的現代技術支撐。只換框架、放大動畫或增加作品數，不能處理目前最明顯的問題：招聘方看得到作品，卻不容易快速判斷你適合哪個職位、實際負責多少、能否處理產品開發的難題。

建議主定位暫定為：**具設計與 UX 能力的前端工程師**。英文輔助定位可採 Frontend Engineer / Design Engineer；在 104 的主要職稱仍用招聘方熟悉的中文名稱。網頁設計與 UI/UX 不是被刪掉，而是成為你在介面品質、跨職能合作與完整交付上的優勢。

建議採取以下整合方案：

1. 首頁從抽象英文標語，改為中文職務定位、具體能力與代表作品。
2. 優先完成三個深入案例，清楚呈現問題、角色、限制、決策、結果與證據。
3. 用一個可操作的 React + TypeScript 功能展示，加上程式碼、測試與技術說明，建立工程證據。
4. 視覺走「編輯式排版 × 精緻產品介面」；保留一個有辨識度的動效，其他動態服從閱讀需求。
5. 預設技術方案為 React + TypeScript + Next.js 的靜態輸出；內容在建置時產生，互動局部載入。若目標職缺或學習成本不適合，依第 9 節改選 Astro + React 或 Vue/Nuxt。
6. 104 履歷、推薦信、網站、可下載履歷使用同一份事實資料，按投遞職類調整呈現順序。
7. 正式開發建立獨立分支與預覽環境，保留現站並具備回復舊版的能力。

這是一份以目前資料能做出的建議，不代表已證實「面試少是網站造成」。目前缺少 104 履歷內容、曝光、投遞數、職缺適配度及面試來源，因果判斷需搭配第 14 節的追蹤。

### 3.3 技術與韌性問題

| 檢查到的證據 | 含義 | 新版要求 |
|---|---|---|
| 遠端 `let/index.html` 約 1,138 行、`main.js` 680 行 | 內容與大量效果耦合；改一種卡片需改多處 | 元件、案例資料、互動邏輯分離 |
| 根目錄及 `let/` 有多份 HTML／資產 | 正式來源容易漂移 | 一份資料與模板，輸出多個所需入口 |
| `package.json` 的 test 是占位命令；未見測試與 CI 配置 | 缺乏可重現的品質證據 | 建置、型別、核心測試、預覽串接 |
| `.gitignore` 排除 `package-lock.json` | 不利於重現完全相同依賴 | 選一種套件管理器並提交鎖檔 |
| H1 兩個文字 span 初始為空，由 JS 逐字注入 | 腳本失敗時核心標題不可見；初次閱讀要等動畫 | 核心文字存在初始 HTML，動畫僅裝飾 |
| Loader 等待 `window.load`；`.reveal-text` 預設透明 | 全 JS 關閉可能被 loader 擋住；某依賴失敗可能留下隱藏內容 | 預設內容可讀，載入失敗仍能看案例與聯絡 |
| Lenis／GSAP 以全域變數直接初始化 | 某外部套件載入失敗可能中斷其後功能 | 打包本地依賴、限制依賴邊界、分段失敗不連鎖 |
| 細指標裝置 CSS 使用 `cursor: none` | 自訂指標未初始化時可能失去可見滑鼠提示 | 主求職路徑保留系統游標 |
| CSS 輪播自動循環，只看到 hover 暫停規則 | 鍵盤／觸控的停止控制需補足 | 封面預設靜止，播放由使用者選擇 |
| 所檢查主檔未找到 reduced-motion、完整選單／dialog 焦點管理 | 尚未建立一致無障礙互動契約 | 以狀態規格及人工測試補齊 |
| 篩選使用延遲 400ms 才隱藏卡片 | 快速切換可能遇到舊計時器覆寫新狀態 | 單一狀態來源，測試快速連點與返回 |
| 動畫 WebP 檔約 4.29 MB、另一檔約 0.63 MB | 轉 WebP 不等於已足夠輕量 | 海報圖先顯示、按需下載動畫或影片 |
| `build:css` 輸出根目錄 assets，但正式站使用 let/assets | 未見腳本明確保證同步 | 建置產物唯一、禁止人工複製當長期流程 |

程式證據：[HTML](https://github.com/colinjen88/letGoWorkRun/blob/e62be5f3bc98cb37ea025488764e48c3fa300463/let/index.html)、[JS](https://github.com/colinjen88/letGoWorkRun/blob/e62be5f3bc98cb37ea025488764e48c3fa300463/let/assets/main.js)、[CSS](https://github.com/colinjen88/letGoWorkRun/blob/e62be5f3bc98cb37ea025488764e48c3fa300463/let/assets/portfolio.css)。這是程式審視與風險推導；快速篩選、CDN 失敗等尚未逐項重現。

### 3.4 對既有規劃的取捨

現有 `portfolio_structure_plan.md` 有值得沿用的案例頁、圖片優化與響應式方向；但以下建議不適合直接延續：

- 全螢幕粒子、固定兩秒品牌載入、到處淡入：增加進入資訊的成本。
- 技能雷達圖與百分比：沒有一致測量尺度，容易變成自評裝飾。
- 同時大量建立 blog、分類子站、聯絡表單：分散求職核心工作。
- 把 F／Z 掃視路徑當成必然閱讀軌跡：版面應依內容與任務測試。
- 「所有影片自動播放」：缺少裝置、資料量及動態偏好考量。

`better.md` 的歷史優化記錄可保留作脈絡，但「降低多少運算」「抵銷 GPU 負擔」等說法，若無同條件量測，不能放進新版作為已驗證成效。

### 4.3 求職定位的策略選擇

你可把三種身分組成一個主張：**能把需求變成高品質介面，並負責前端實作與驗證**。這比三個平行職稱更容易被記住。

優先職缺可分為：

1. **UI 品質導向的前端／UI Engineer**：重視細節、設計系統與介面實作，最能連結三種能力。
2. **產品前端工程師**：需要強化 API、狀態、資料處理與測試；技術 demo 的重要性最高。
3. **網頁／UI 設計師且需要前端落地**：重視品牌、RWD、原型及交付；設計案例比框架名稱重要。
4. **純研究型 UX 職位**：只有在具備訪談、研究設計、分析與驗證證據時才重點投遞；美術與切版經驗不能直接替代研究經驗。

正式實作前，以你想投的 15–20 個職缺建立矩陣：職類、地區、年資、必要技能、已有證據、待補證據、意願。這是下一階段的個人化工作，本次沒有假稱已完成 20 職缺量化分析。

### 4.4 能力深度與誠實呈現

技能不用星等，改成「能做的工作＋證據位置」：

| 能力層級 | 寫法 | 舉例格式 |
|---|---|---|
| 能獨立交付 | 具體責任與範圍 | 獨立實作某流程與響應式介面，連到案例 |
| 能協作完成 | 清楚交代分工 | 與後端協作完成 API 契約與錯誤顯示 |
| 新近補強 | 標示新實作與日期 | 2026 改版中導入 TypeScript 與自動化測試 |
| 尚未掌握 | 不放熟練技能欄 | 作為內部學習清單，完成後再公開 |

不要因為新版採 React 就回寫成多年 React 經驗；也不要把 AI 產出的功能等同於自己已熟練。至少能現場解釋資料流、指出限制、修改一個需求並修復測試，才是可用的工程證據。

### 5.2 從招聘研究得到的內容方向

NN/g 的作品集研究強調過程、貢獻、限制與實際價值，不只看最終畫面；其建議也是選擇少量有深度的代表案例。對本案的應用是：三個案例先完成，讓閱讀者能迅速找到你做的決策，再自行展開細節。[研究來源](https://www.nngroup.com/articles/ux-design-portfolios/)

初篩者也可能是非設計背景的招聘人員、PM 或創辦人。因此首頁需使用一般工作語言；詳細頁再提供工程與設計深度。這支持「摘要＋細節」的呈現，而非把一整套 UX 教科書搬進案例。[招聘訪談整理](https://www.nngroup.com/articles/ux-hiring-insights/)

### 6.2 建議網站結構

├─ 精選案例 /work/

首頁與案例以同一份內容資料產生。不同職類入口只改摘要、案例排序與強調點，不複製維護兩套網站，也不讓首次訪客必須先選身分才能進站。

### 6.3 首頁內容順序

1. **身份與價值**：姓名、中文主要職稱、一句可核實能力、目前求職條件（待確認）。
2. **主行動**：「查看精選案例」；次行動：「查看／下載履歷」；聯絡方式始終可找到。
3. **代表案例預告**：桌機首屏可看到至少一個案例訊號；手機在下一個自然捲動位置看到代表作品。
4. **三個精選案例**：每張卡含角色、問題、實作／成果及深入連結。
5. **能力證據**：元件、可操作流程、品質檢測與對應案例。
6. **經歷與協作**：精簡時間軸與一個合作實例。
7. **延伸作品**：動效、平面、其他網站；次於求職主線。
8. **面試聯絡**：Email、履歷、GitHub（有合適內容）、工作條件與更新日期。

### 6.4 首頁文案提案

暫定主標：

> 我是 WANG，結合設計與 UX 的前端工程師。

暫定副標：

> 從需求與操作流程出發，完成響應式介面、互動設計與前端實作。這裡整理了我的專案分工、設計取捨與技術實作。

待框架展示完成後，可在能力列加入「React / TypeScript」，並連到實際成果。原本英文標語可保留於較次要的位置，或轉成 Motion Lab 的主題。

求職聯絡文案：

> 正在尋找前端工程師／介面開發相關機會。歡迎透過 Email 聯繫，討論團隊需求與面試安排。

若最終主投設計，改成：「我是 WANG，能將介面設計落實為前端產品的 UI／網頁設計師。」這是選定定位後的替換稿，兩句不並列搶焦點。

### 7.2 每個完整案例的標準模板

1. **30 秒摘要**：專案是什麼、你負責什麼、解決什麼、現在狀態。
2. **基本資料**：時間、類型（商業／個人／試做）、團隊、本人職責、公開範圍。
3. **問題與限制**：使用者任務、原有痛點、時程／成本／技術限制。
4. **證據來源**：需求文件、訪談、觀察、操作紀錄、數據；若無研究則明寫。
5. **關鍵決策 2–3 個**：考慮的方案、選擇理由、放棄的代價。
6. **介面與狀態**：主流程、空資料、錯誤、長內容、手機與鍵盤狀態。
7. **工程實作**：資料流、元件邊界、API／狀態、效能、測試與部署。
8. **驗證與成果**：有日期與條件的數據、使用者回饋或可重現的任務測試。
9. **限制與反思**：尚未做到的事、下一次會如何調整。
10. **證據連結與下一步**：實站、程式、原型、下一案例、面試聯絡。

正文初稿可抓 800–1,500 個中文字，搭配 6–10 張有說明的圖；工程細節置於附錄或展開區。這是編輯工作量起點，依內容調整，不為了字數灌水。

### 7.3 範例：把模糊標籤轉成有內容的案例

原敘述：「RWD • UI/UX • 後台 • 微互動」。

可採用的案例標題草稿：「讓訪客找到合適課程，也讓營運人員維護內容」。

摘要欄位：

| 欄位 | 填寫規格 |
|---|---|
| 我的角色 | 例如介面設計與前端；實際分工待核實 |
| 問題 | 具體描述哪種使用者在何種操作遇到障礙 |
| 決策 | 例如課程分類、資料更新流程、行動版資訊優先順序；不能當成已發生事實 |
| 實作 | 使用到的真實技術、元件與 API 契約 |
| 結果 | 真實量測；若沒有商業數據，改列測試結果與已交付範圍 |
| 尚未驗證 | 例如營收、報名轉換或長期維護成本 |

每張截圖都應回答一個問題，例如「這個欄位錯誤提示如何協助使用者修正」，而非單純增加漂亮畫面。

### 7.4 成果與研究的真實性規格

- 沒有 GA／Search Console／業務資料，就不寫轉換提升、營收提升或排名成長百分比。
- 可以做現在的重測，標示「2026 年回顧測試」，不可回填成當時做過的研究。
- 量測須列前後版本、工具、裝置、網路條件、日期與樣本；只對可比部分下結論。
- 試做案例清楚標示非委託／未商用，不暗示品牌聘用或推薦。
- 團隊作品列本人責任與他人責任；推薦語需真實且獲授權。
- 後台展示使用清理過的截圖或示範資料，公開 repo 移除個資、密鑰及不宜公開的商業資料。

## 8. 視覺、品牌與互動升級

### 8.1 三種設計方向

| 方向 | 視覺語言 | 適合 | 成本／風險 | 建議 |
|---|---|---|---|---|
| A：編輯式作品集 | 淺暖底、深色字、非對稱網格、大幅作品、精確留白 | 前端＋設計的整合定位 | 需高品質圖片與文字編輯，不能靠背景特效撐場 | 主推薦 |
| B：精緻深色產品介面 | 深中性色、單一強調色、緊湊資訊、細緻元件狀態 | 產品前端、Design Engineer | 若沿用大量漸層光暈，辨識度提升有限 | 可選；不是深色本身有問題 |
| C：動態創意工作室 | 更強個性字體、動態排版、局部 3D／Canvas | Creative Developer、互動設計 | 工時、低階裝置與閱讀門檻較高 | 作為 Lab 或特定投遞版本 |

本案建議採 A 為主，於工程展示區局部使用 B；C 的特色濃縮成一個短而可控制的動效。風格選擇是本案設計判斷，並無研究能保證淺色一定比深色獲得更多面試。

### 8.2 視覺品質應升級在哪裡

- **字體層級**：中文資訊成為主體；英文提供節奏。桌機展示字約 48–72px、手機 32–44px，使用 fluid type，避免長中文標題強制斷裂。
- **正文可讀性**：正文初始 17–18px、行高約 1.65–1.85；用實際繁中字樣與窄螢幕調整，不以英文 ch 值直接當中文字數。
- **網格**：桌機 12 欄、手機 4 欄作設計基準；案例閱讀欄約 680–760px，圖像可跨至 1120–1280px。
- **視覺節奏**：一張大主案例加兩張次案例，讓重點可見；完整列表保持掃讀秩序，不做會改變閱讀順序的瀑布流。
- **作品封面**：統一外框比例，依作品內容選真實界面、品牌局部或一個關鍵操作；不把整張長頁縮小到看不清。
- **圖片敘事**：封面、局部細節、流程與手機圖各有用途；避免同一截圖反覆出現。
- **識別**：把泛用 P. PORTFOLIO 換為可辨識的姓名／字標。識別要可縮放、可作 favicon，不必先花多週做複雜 Logo。
- **文案品質**：修正文法、命名與中英文空格一致性；例如「形像」改為「形象」，並具體標示真實專案名稱。

視覺階層、對比、比例與群組能共同幫助理解；採用這些原則不等於只追求極簡。[NN/g 視覺設計原則](https://www.nngroup.com/articles/principles-visual-design/)

### 8.3 設計 Token 起稿

| 類別 | 暫定值 | 使用要求 |
|---|---|---|
| Canvas | `#F7F7F2` | 大面積背景 |
| Surface | `#FFFFFF` | 功能表面與局部卡片 |
| Ink | `#18231F` | 主要文字 |
| Muted text | `#53635B` | 次要文字；實作時驗證對比 |
| Accent | `#245C47` | 主要行動、連結及焦點 |
| Border | `#D4DDD6` | 分隔與邊框；不可單靠低對比邊框表達必要狀態 |
| Spacing | 4、8、12、16、24、32、48、64、96 | 建立語意用途，避免隨處加 magic number |
| Radius | 8、16、24 | 小控制項、卡片、重點容器 |
| Motion | 120–180ms 微回饋；200–300ms 切換 | 不為閱讀加入固定等待 |

這是供設計比較的起稿，不是已核准視覺。最終需建立色彩配對表，分別檢驗文字、連結、focus、錯誤及 disabled 狀態。

### 8.4 應保留的招牌動效

建議設計「同一個元件從需求註記、版面格線到完成介面的轉換」。它能直接表達設計與工程的連結，與你的職務定位一致。

功能規格：預設先顯示完成介面；使用者可按播放查看 2–4 秒示範；不遮住主標與 CTA；支援暫停、鍵盤及 reduced motion。若實作壓力過高，先用簡單 CSS／SVG 版完成，晚一階段再增加細節。

將滑鼠拖尾、磁吸按鈕、夜間流星、Konami 彩蛋、大範圍 tilt 移到可選 Lab。主要求職流程保留原生游標、捲動與連結行為。

### 8.5 Figma 與程式碼交付一致性

建議交付一份小而完整的設計系統：Foundations、Components、Page templates、Prototype 四部分。先完成按鈕、文字連結、案例卡、標籤、導覽、gallery、通知及 demo 表單／資料列。

每個元件對齊名稱、Token、variant、互動與狀態；Figma Auto Layout 與程式的響應式行為需能互相解釋。保留一次「設計變數調整→程式同步→驗證」的實例，作為跨設計與工程的證據，不只截一張元件牆。

## 9. 前端技術選型與架構

### 9.1 選型比較

| 路線 | 優點 | 代價／限制 | 本案適用性 |
|---|---|---|---|
| 整理原生 HTML/CSS/JS | 改動小、託管簡單、基本內容可快速改善 | 案例增加後需自行處理模板與資料；框架證據不足 | 適合緊急求職修正版 |
| Astro + TypeScript + 少量 React | 內容站與案例自然；靜態 HTML，互動按區塊啟動 | Astro 經驗不等於 React 應用架構經驗，需獨立 demo | 內容維護與低 JS 優先時的強選項 |
| Next.js + React + TypeScript | 路由、元件、靜態產出與 React 能力在同一專案 | Client 邊界需管理；靜態輸出有功能限制 | 前端主投時的預設建議 |
| Vue/Nuxt + TypeScript | 若你已有 Vue 實務，能用更低成本展示更深品質 | 同時學 React 與 Vue 會分散深度 | 目標職缺／既有經驗偏 Vue 時取代上一列 |

Astro 官方說明其 HTML 與互動 islands 的分工；Next.js 官方支援逐路由靜態輸出並列出限制。兩者都能做出快或慢的網站，不能只看框架名稱下結論。[Astro Islands](https://docs.astro.build/en/concepts/islands/)、[Next.js Static Exports](https://nextjs.org/docs/app/guides/static-exports)

### 9.2 預設方案與決策門檻

**預設：Next.js + React + TypeScript，案例預先產生，靜態輸出部署。** 原因是本次主假設為前端求職，需要讓元件、型別與互動展示有一條可查驗的技術線。

在前期定位與內容盤點期間，用一個案例頁＋一個小型資料互動完成技術試作，最晚在視覺與技術定稿前確認：

1. 你能解釋 props、state、渲染、事件與非同步狀態。
2. 靜態輸出可正確處理案例路由、圖片與目前託管環境。
3. 初始載入與內容維護成本符合預算。
4. 目標職缺沒有更強的 Vue 優先訊號。

若試作顯示框架學習將明顯拖延求職，改用 Astro + React 局部展示；若你已有更深 Vue 經驗且目標職缺吻合，使用 Vue/Nuxt。只選一個主應用框架，不在同一作品集堆入三種框架。

### 9.3 靜態站與功能展示的邊界

首頁、案例、履歷、設計系統說明均在 build 產生 HTML。React 互動限於 gallery、篩選與功能 demo；不要整頁都標成 Client Component。

Next.js 靜態輸出不提供需要伺服器的 Server Actions、動態 request 邏輯、預設圖片最佳化等功能。圖片需使用建置時處理或合適 loader；路由須可於建置時列舉。Redirect 與 HTTP headers 由實際託管層處理。若未來新增私有 API，需另行規劃 server runtime，不把密鑰塞進前端。[官方限制](https://nextjs.org/docs/app/guides/static-exports#unsupported-features)

### 9.4 建議程式結構

```text
src/
├─ app/                  路由、layout、metadata、案例頁
├─ components/
│  ├─ ui/                基本控制項與狀態
│  ├─ portfolio/         案例卡、摘要、圖集、證據區
│  └─ lab/               唯一的功能展示
├─ content/work/         Markdown／MDX 與案例資料
├─ lib/                  schema、資料轉換、工具與事件定義
└─ styles/               Token、base、版面與特定元件
public/                  公開靜態資產及履歷
tests/                   核心單元／整合／端對端測試
docs/                    架構決策、內容指南、部署與回復手冊
```

內容模型包含：slug、title、summary、projectType、role、period、team、problem、constraints、decisions、stack、evidence、outcomes、limitations、links、cover、featured。`outcomes` 需有 evidence 或明確標示未量測；schema 驗證缺少角色／狀態的案例不得進入正式精選列表。

採 Git 管理 Markdown／結構化資料即可。CMS 留待需要頻繁非技術編輯或多人協作時評估。Astro 路線則使用 Content Collections 的 schema 機制達到相同目的。[Astro Content Collections](https://docs.astro.build/en/guides/content-collections/)

### 9.5 值得投資的現代能力

| 技術／能力 | 本次具體用途 | 優先級 |
|---|---|---|
| TypeScript strict | 案例 schema、API 型別、UI 狀態，降低資料錯配 | P0 |
| React 元件與狀態設計 | 有意義的互動流程；分清伺服器資料與 UI 狀態 | P0 |

### 9.6 AI 協作的呈現方式

Antigravity 等工具經驗可轉成一小段真實工作流程：如何拆解任務、檢查產物、判斷方案與驗證。展示一次 AI 建議被你修改／否決的具體決策，比只列工具名稱更能說明判斷能力。

首版不加入 AI 聊天履歷助手。它增加維護、錯誤回答與閱讀負擔，而且不如清楚的履歷和案例直接。若未來針對 AI 前端職缺新增，需有來源引用、錯誤狀態與費用控制的獨立範圍。

## 10. 招牌工程展示的最小可行規格

建議從現有作品延伸「資料更新狀態看板」，或「預約流程元件」，二選一完成。不是另造一個與經歷無關的大型產品。

### 10.1 首選：資料看板展示

| 面向 | 規格 |
|---|---|
| 情境 | 使用者需要判斷資料是否新鮮、能否信任、如何處理失敗 |
| 資料 | 使用有來源說明的固定 fixture／模擬 API；標示「示範資料」 |
| 操作 | 篩選、排序、更新、切換成功／空資料／延遲／部分失敗 |
| 狀態 | idle、loading、success、empty、stale、partial-error、error |
| 工程重點 | runtime 驗證、race condition／過期回應處理、取消請求、格式化與可測性 |
| UX 重點 | 保留可用舊資料、顯示更新時间、可恢復錯誤、避免每次整頁閃白 |
| 可查驗成果 | 程式碼、README、架構圖、測試與三分鐘操作說明 |
| 範圍排除 | 真實交易、真實用戶帳號、新增採集服務、後台機密資料 |

不要為了展示而過度使用全域 state store；能用區域狀態完成就清楚說明理由。若需要資料快取套件，以具體重試與快取需求論證，不當成履歷裝飾。

### 10.2 核心測試案例

- 快速切換篩選後，較晚回來的舊請求不覆寫新資料。
- 部分來源失敗時，其他資料仍能閱讀，並顯示失敗範圍。
- 資料過期與正常資料視覺不同，但不是只靠顏色區分。
- 鍵盤能完成篩選與重試；載入／錯誤狀態可被讀屏理解。
- 窄螢幕仍保留資料名稱、值、單位與時間的關係。

測試是對真實使用風險，而非只是斷言實作內部變數。此展示能同時成為技術、UX 與可存取設計案例。

## 11. 行銷心理、視覺心理與 UX 規格

目標是幫招聘方理解與作決策。「完美」應轉化成可驗證的品質要求；不能靠心理學名稱或視覺效果保證結果。

### 11.1 原則如何落地

| 原則 | 本案的具體設計 | 要驗證什麼 |
|---|---|---|
| 審美與可信度 | 統一文字、留白、圖片處理、控制項品質 | 第一印象專業度；不把好看評分當成可用性通過 |
| 視覺階層與群組 | 角色、案例、結果形成穩定順序；說明靠近對應圖 | 看完卡片能否說出你做了什麼 |
| 資訊線索 | 「查看預約流程案例」勝於無意義的 Explore；標記外站 | 點擊前能否預測目的地 |
| 漸進揭露 | 先摘要，再詳細證據；技術附錄按需展開 | 初篩者與主管是否都能找到所需深度 |
| 辨識勝於記憶 | 每個案例用一致欄位，返回列表保留位置 | 比較兩個案例時不需來回記憶 |
| 認知負荷 | 首頁三件精選，完整列表再篩選 | 讀者能否快速挑到與職位相關案例 |
| 控制感 | 可停止動效、正常返回、明確外站提示 | 沒有被動畫或新分頁困住 |
| 不確定性降低 | 標示本人貢獻、專案類型、真實數據與限制 | 是否能分辨商業成果與試做 |

審美確實會影響人對可用性的感受，但不能彌補嚴重操作障礙。[審美可用性效應](https://www.nngroup.com/articles/aesthetic-usability-effect/)

資訊標籤與漸進揭露的設計依據分別見 [Information Scent](https://www.nngroup.com/articles/information-scent/) 與 [Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)。控制、回饋、辨識與一致性來自通用設計準則，仍需在本案測試。[NN/g 十項準則](https://www.nngroup.com/articles/ten-usability-heuristics/)

### 11.2 不採用的心理話術

不使用假推薦、假瀏覽人數、假錄取數、虛構大客戶、倒數計時或稀缺暗示。也不套用「某顏色必定提高轉換」「招聘方一定只看六秒」「五位受測者即可證明全面成功」等過度簡化說法。

你的說服力應來自讓招聘方更少猜測：你做什麼、做得如何、可以怎麼查證。

### 11.3 元件與互動狀態契約

| 元件 | 必備狀態／行為 |
|---|---|
| 導覽 | 當前位置、鍵盤焦點、mobile expanded、Esc 關閉、回復焦點；不擋住標題 |
| 案例卡 | 靜態可讀、hover／focus 一致、連結用途明確；不巢狀放互相衝突的連結 |
| 篩選 | 可分享狀態、選取標記、結果數、清除、無結果；快速連點正確 |
| 圖集 | 前後、位置／總數、圖片說明、鍵盤、觸控；不強制 autoplay |
| Dialog | 有名稱、初始焦點、焦點限制、Esc、關閉控制、關閉後回到來源 |
| 複製 Email | 成功回饋、失敗時保留可選文字、正常 mailto 備援 |
| 媒體 | 海報、可操作播放／停止、影片必要字幕／文字摘要 |
| 外部連結 | 清楚區分實站與案例；新分頁有提示及安全屬性 |
| 404／空頁 | 可理解說明、返回作品入口、避免看起來像伺服器故障 |

Dialog 依 [W3C APG Modal Dialog Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) 實作與驗證；優先用原生元素或成熟可存取基礎元件，仍需自己測試整合結果。

### 11.4 無障礙目標

整體以 WCAG 2.2 AA 為目標；驗收不只依賴掃描分數。

- 一般文字對比至少 4.5:1，大字至少 3:1；必要控制項與視覺資訊另檢查適用的非文字對比要求。
- 明顯且不被固定區塊遮住的焦點、Skip link、語意標題與正確語言設定。
- 主要觸控控制項以 44×44 CSS px 作內部設計目標；WCAG 2.2 AA 2.5.8 的最低基準是 24×24 且有例外，不能混稱。
- 使用 `prefers-reduced-motion` 降低非必要動畫；長時間自動播放的資訊提供適用的停止控制。
- 200% 文字縮放、320 CSS px 寬重排，必要二維資料可在有說明的區域內橫捲。
- 裝飾圖不重複朗讀，內容圖有用途導向的替代文字。

基準：[WCAG 2.2 Quick Reference](https://www.w3.org/WAI/WCAG22/quickref/)、[MDN reduced motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)。以上只摘要本案優先項目，不能取代完整合規檢查。

## 12. 效能、SEO、可靠性與維運

### 12.1 效能目標與量測方式

| 指標 | 目標 | 方法與限制 |
|---|---|---|
| LCP | ≤ 2.5 秒 | 真實使用者第 75 百分位，手機／桌機分開看 |
| INP | ≤ 200ms | 同上；需有實際互動資料 |
| CLS | ≤ 0.1 | 同上；圖片、字體與動畫不推動版面 |
| Lighthouse Performance | 行動版代表頁中位數 ≥ 90 作內部目標 | 固定工具版本、節流、裝置模擬，至少三次；不是錄取指標 |
| 首次必要 JS | 先抓壓縮後 ≤ 150 KB | 含首屏必要套件，排除明確按需 demo；试作後驗證可行性 |
| 首屏必要下載 | 先抓 ≤ 1 MB | 包含首屏圖、字體、CSS、JS；不含使用者主動播放媒體 |
| 重型媒體 | 首屏不下載大型動畫 | 圖片先占位、影片按需、合理 preload |

前三項是官方 Core Web Vitals 良好門檻；其他是本案工程預算，不是通用標準。[web.dev Web Vitals](https://web.dev/articles/vitals)

若流量不足以取得穩定的現場資料，標示「資料不足」，以實驗室測試與手動操作作為上線前依據，不能宣稱已達到真實使用者 p75。

優化順序：先移除阻擋內容的 loader → 控制圖片尺寸與格式 → 提供 width/height 或 aspect-ratio → 限制初始 JS → 字體字重／子集與 fallback → 查看互動 long tasks → 最後調整裝飾細節。不要把全部圖片都 lazy load；首屏重要圖應正確設定載入優先級。

### 12.2 SEO 與分享

求職短期轉換以 104 入口為先，SEO 是可發現性與專業整潔度的補充。

- 每頁 title、description、canonical，案例有獨立 URL。
- 首頁 OG 圖改成你的姓名、職稱與代表作品，而非單一客戶官網縮圖。
- 產生 sitemap／robots；預覽環境 noindex，機密內容另外限制存取。
- 使用真實 Person／ProfilePage 等適合內容的結構化資訊；不捏造評分或任職資訊。
- 舊錨點 `#about`、`#expertise`、`#works`、`#whyme`、`#contact` 保持有合理落點。
- URL fragment 不會傳到伺服器：舊 hash 對應需保留頁面 id 或前端處理，不能只靠伺服器 redirect。
- `job.html`、`jobs.html`、`tri.html`、舊 PDF 及 `/let/` 路徑先盤點實際被使用的網址，再建立逐筆映射；不把所有舊網址粗略導回首頁。
- 跨職類入口若幾乎相同，處理 canonical／noindex；若內容實質不同，使用自有 canonical。

### 12.3 部署與可靠性

將「首次主機建置」與「網站更新」分開。既有腳本混合 apt 安裝、憑證、git pull、權限及服務重啟，不適合作為每次一般改版發布的唯一工具。

建議流程：CI 建置測試 → 產出帶 commit SHA 的靜態包 → 預覽驗證 → 上傳獨立 release 目錄 → 切換正式指向 → 核心路徑檢查 → 可切回前一 release。一般部署不需要反覆更新系統套件或重建憑證。

託管先沿用既有環境，確認 VPS 與代理設定後再決定是否搬遷；不把搬平台當改版必備工作。建置使用鎖檔與相容 runtime；CI 執行必要檢查，部署權限只在發布流程使用。[GitHub Node.js CI 文件](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs)

資產使用內容雜湊檔名配合長快取，HTML 使用適合更新頻率的快取策略。公開產物不包含 `.git`、內部部署資訊或未清理素材。HTTP headers 依實際嵌入服務與 CSP 需求設定，先預覽檢查，再上正式環境。

## 13. 104 履歷與作品集的整合

### 13.1 同一個事實來源，依職缺換排序

建立內部「求職事實表」：任職期間、職稱、責任、作品類型、技術、量測、可公開連結。104、履歷 PDF、網站及自我介紹皆從這份資料取用。

## 14. 成效追蹤：知道哪裡流失，才知道怎麼改

### 14.1 招聘漏斗

```text
合適職缺與履歷曝光
    ↓
履歷被查看／投遞被閱讀
    ↓
網站到訪 → 案例深入 → 履歷／聯絡意圖
    ↓
實際面試邀約 → 面試 → 後續進展
```

網站只能直接觀測中間一段；招聘方也可能看完後回 104 發邀約，不點 Email，因此網站點擊不是最終轉換。

### 14.2 指標定義

| 指標 | 定義 | 如何使用 |
|---|---|---|
| 合適投遞回覆率 | 有回覆的合適投遞／合適投遞數 | 分前端／設計、地區與資歷要求記錄 |
| 面試邀約率 | 產生面試邀約的合適投遞／同批合適投遞數 | 固定觀察窗口，例如 21 天；未成熟批次分開 |
| 自發邀約數 | 非當批主動投遞而收到的相關邀約 | 單獨計數，不硬除以未知曝光量 |
| 案例深入率 | 開啟至少一個案例的有效網站工作階段／有效到訪 | 分來源、裝置與版本；無法辨識是否真招聘者 |
| 聯絡意圖率 | 有 Email／履歷動作的工作階段／有效到訪 | 中間指標，不等於寄信或面試 |
| 測試任務成功率 | 不經協助找到正確證據的任務／總任務 | 確認資訊架構是否有效 |

第一週回填最近 4–8 週可取得的求職資料；沒有就從現在開始。不能先宣稱要提高 200%，也不把低樣本的 1 次／10 次對 2 次／10 次視為穩定翻倍。

### 14.3 事件規劃

可用事件：`case_open`、`evidence_open`、`demo_start`、`resume_click`、`email_click`、`email_copy_success`。附帶經允許的 `page_id`、`case_id`、`portfolio_version`、泛用來源類別；不要傳 Email、履歷內容、公司名或其他個人資料。

104 入口可用泛用 `utm_source=104`、`utm_medium=resume`、`utm_campaign=frontend_v2`，只代表這個連結的使用來源，不代表能識別招聘公司。Referrer 缺失、預覽機器人、阻擋追蹤與跨裝置都會影響資料；接受缺失，不做指紋追蹤。

分析工具選擇在實作時依既有服務與需求決定；首版只保留必要事件，不預設錄製訪客操作影片。

### 14.4 小流量驗證策略

優先做兩輪任務測試，每輪約 5 位相關參與者：可混合招聘、工程主管、設計主管或相近角色。若暫時找不到真正招聘方，標註同儕測試，不能當作招聘研究。兩輪盡量避免完全相同受測者造成學習偏差。

任務示例：

1. 看首頁後，說出這個人主要應徵什麼，以及一個差異化能力。
2. 找到一個能證明 API／狀態處理能力的案例，說出他的貢獻。
3. 找到一個設計決策及支持它的證據。
4. 在手機上找到履歷與聯絡方式。
5. 看案例後說出仍讓你猶豫邀請面試的資訊。

內部門檻可先設：每輪至少 4/5 能完成核心尋找任務，且沒有重複出現的嚴重障礙。這是迭代門檻，不是統計顯著性或五人就足夠的普遍定律。

新版上線後觀察 4–6 週，分批記錄相近職類的投遞與邀約。先做方向性比較；若招聘季節、投遞策略或履歷同時改變，需承認混雜因素。低流量情況下，不把首頁切成大量 A/B 分流。

## 15. 分支、遷移與上線策略

**需要建立新分支。** 大幅更換結構、路由與資產會影響目前求職入口，應有獨立開發與預覽。這一階段交付計劃書即可，正式開發再建立分支。

建議分支名稱：`codex/portfolio-v2`；起點為開工時重新取得並審視的 `origin/master`。目前基準是 `e62be5f`，不能直接從落後 15 個提交的本機版本開始改。

操作順序：

1. 檢查工作目錄，保留本計劃與任何新修改。
2. 更新遠端參照並確認新版差異；不執行會丟失工作內容的重設。
3. 從確認過的最新遠端建立改版分支；需要並行維護舊站時，可用獨立 worktree。
4. 在新分支建立新應用來源與建置流程，不以發布時覆蓋舊目錄作回復機制。
5. 一份案例、一個互動先打通設計→建置→預覽→檢查。
6. 完成內容與驗收後產生候選 release，列明 commit、網址映射與檢查結果。
7. 切換正式站，檢查 104 常用入口、案例、媒體、履歷與聯絡。
8. 如核心入口故障、主要資產大量失敗或內容不可讀，切回上一 release。

回復演練需在預覽環境實際做過；保留上一份 build 與相容 headers／路由設定。只保存 Git tag 但沒有可部署產物，不算完整的回復準備。

## 16. 執行階段、工作量與優先級

### 16.1 建議主線：4–6 週可投遞版本

以下為「材料大致可取得、每週有 25–30 小時有效投入」的工作估算，不是自動化可保證的工時。若每週約 20 小時，含緩衝應抓約 5–8 週；若只有每週 10 小時，或需從零建立框架能力與案例素材，日曆時間要再延長。

| 階段 | 估計投入 | 主要交付 | 依賴／完成門檻 |
|---|---:|---|---|
| 0. 定位與材料盤點 | 6–10 小時 | 求職事實表、目標職缺矩陣、案例選擇 | 主要職類及可公開材料 |
| 1. 內容與 UX 架構 | 12–18 小時 | 三案例大綱、一案例完整稿、首頁文案、線框 | 能清楚說明本人貢獻 |
| 2. 視覺方向與技術試作 | 12–18 小時 | 兩方向比較、定稿 Token、一頁試作 | 技術可行、視覺與閱讀均通過 |
| 3. 核心頁面與案例 | 20–30 小時 | 首頁、三案例、履歷、聯絡、響應式 | 內容完整與路由可用 |
| 4. 工程展示與品質 | 14–22 小時 | 一個可操作 demo、核心測試、程式說明 | 可解釋與可重現 |
| 5. 驗證、遷移與發布 | 10–16 小時 | 使用測試、效能、無障礙、redirect、回復 | 所有 P0 完成 |
| 合計 | 74–114 小時 | 第一個可投遞完整版本 | 加 15–25% 緩衝約 85–143 小時 |

第 2 週可形成一個「首頁＋一完整案例」的審閱版本；第 4–6 週是推薦發布窗口，仍以品質與材料完成度決定，不為日期虛構內容。參與者約訪、取得授權與補資料的等待時間可能另加。

### 16.2 快速版與完整版

| 路線 | 工程規模 | 適用條件 | 不包含 |
|---|---|---|---|
| 快速改善，約 1–2 週、20–35 小時 | 改定位與順序、補一案例、修 loader／降級、整理聯絡 | 現在需要繼續投遞、完整改版時間不足 | 全新框架與完整設計系統 |
| 推薦主線，約 4–6 週 | 全新視覺與結構、三案例、一 demo、品質與遷移 | 願意系統提升作品集 | 大型 blog、CMS、完整多語系 |
| 第二階段，另估 20–40 小時 | 設計入口、更多 Lab、英文摘要、設計系統文件 | 核心內容已證明有用且維護得來 | 沒有需求的功能堆疊 |

快速版是替代或先行的範圍選擇，若先做再做完整版，需計算重用與額外成本，不能視為免費附加。

## 17. 上線驗收與「完成」定義

| 面向 | 必須通過 |
|---|---|
| 定位 | 首頁、Title、履歷與 104 主要職稱一致；關鍵資訊在初始內容即可取得 |
| 案例 | 精選作品角色、專案類型、問題、決策、證據與限制完整；無虛構成效 |
| 視覺 | 360／390、768、1280／1440px 等代表尺寸檢查；另看 320px 重排與長內容 |
| 主流程 | 首頁→案例→證據→履歷／聯絡可完成，返回不迷路 |
| 跨瀏覽器 | Chrome／Edge、Firefox、Safari／iOS 的核心路徑；WebKit 模擬不取代真實 iPhone 檢查 |
| 互動 | 快速篩選、空狀態、錯誤、重試、失敗備援有預期結果 |
| 無障礙 | 鍵盤、focus、dialog、圖像說明、對比與動態偏好人工檢查；自動掃描只作輔助 |
| 效能 | 代表首頁／案例／demo 有固定條件報告；超出預算有修正或明確取捨 |
| 工程 | fresh install、型別、build、核心測試可重現；公開 repo 有可理解 README |
| 韌性 | JS 停用／某外部資產失敗時核心內容與聯絡可用；影片不是唯一證據 |
| 發布 | 網址映射、404、分享資訊、舊連結與回復驗證完成 |
| 求職 | 投遞版本與作品連結一致，開始記錄來源及邀約 |

不以「所有 Lighthouse 項目 100」「所有心理學法則都用上」「動畫最多」定義完成。完成是：目標讀者能理解、能查證、能聯絡，且你能解释網站的設計與工程決策。

## 18. 風險與調整方案

| 風險 | 早期訊號 | 處理 |
|---|---|---|
| 首頁定位過廣 | 受測者無法說出主投職位 | 縮成一個主職稱，其他能力作證據 |
| 框架學習壓過內容 | 一週仍無可讀案例試作 | 採更熟悉方案，框架 demo 縮小 |
| 案例缺資料 | 只有截圖，說不出本人決策 | 改選有證據作品；新增真實回顧測試 |
| 視覺普通或模板化 | 略換配色卻沒有自己的作品語言 | 重做封面與排版，而非再加光暈 |
| 動效降低可用性 | 看不到重點、手機掉幀、閱讀中斷 | 移至 Lab、改為主動播放 |
| 多入口維護漂移 | 職稱、日期與成果互相矛盾 | 共用資料，schema 與內容審核 |
| 新版改善但邀約仍少 | 網站可讀性提升、合適邀約仍低 | 分析職缺適配、履歷曝光與投遞策略，不無限改 UI |
| 分析資料不足 | 有效訪問稀少或機器人占比高 | 用質性測試與投遞紀錄補充，不硬算顯著性 |
| 誤操作正式環境 | 發布依賴不明的舊腳本 | 先確認實際託管拓樸與 release 流程 |

## 19. 接下來最有價值的五項資料

這些資料用於精準化下一版計劃，不影響本計劃先完成：

1. 你主要想投的職位、地區、工作型態與薪資區間。
2. 去除不必要個資的 104 履歷，以及最近投遞的 5–10 個代表職缺。
3. React／Vue／TypeScript 的實際使用經驗：做過什麼、能獨立解釋到哪裡。
4. 最熟悉的三個作品：本人分工、時間、限制、設計稿／程式與可公開範圍。
5. 最近 4–8 週能取得的投遞、被閱讀、回覆、邀約資料；沒有則從現在開始。

若只先做一件事，應先確認主定位並完成第一篇有證據的完整案例。它會決定首頁文案、視覺重點與工程展示，而不是先從動畫或框架版本開始。
